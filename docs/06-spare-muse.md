# 06 — Spare Muse

The proposed spare-Muse model treats the host as replaceable and accepts failure risk. Resilience still requires independent backups, access control, monitoring, patching, clear ownership, integrity checks, and a documented restore process.

Define RPO/RTO, replication schedule, encryption, credential recovery, failover method, DNS behavior, and test cadence. A second device or account is not a backup if it shares the same failure domain. Keep site source in Git and export configuration in a portable format. See [the HTML spare-Muse notes](../spare-muse.html).
